## 3. 完成版で遊べる内容

### 3.1 ルールと操作

攻撃が中央の基準へ届く瞬間に、来た方向と反対のボタンを押します。攻撃は左・右・上・左上・右上の5方向です。下部には左・左下・下・右下・右の5ボタンを固定配置し、難易度が変わっても場所を動かしません。

| 攻撃が来る方向 | 押す方向 | PCの既存操作を引き継ぐキー |
| --- | --- | --- |
| 左 | 右 | → / D |
| 右 | 左 | ← / A |
| 上 | 下 | ↓ / S |
| 左上 | 右下 | E / C |
| 右上 | 左下 | Q / Z |

PCでも画面内ボタンをマウスで押せます。キーの自由な割り当て機能は今回追加しません。長押しの繰り返し入力、同じ押下から発生する互換イベントによる二重判定は無効にします。方向ボタン以外の画面タップは攻撃入力にしません。

1攻撃は同じ方向への1〜3回の押下で受け流します。各回の到達時刻、必要回数、残り回数を見た目でも確認できるようにします。1押下を複数回へ割り当てません。同時押しを総当たりの成功にせず、同時刻の異方向入力は固定した順序で1件だけ採用します。その順序は端末や描画頻度で変えません。

次に押す対象は最も手前の未判定部分です。最初の部分は攻撃出現から入力対象とし、早すぎる入力は失敗です。2個目以降は前の部分が判定済みで、かつ自分の成功受付開始時刻を迎えてから入力対象とします。それ以前の追加入力は無視し、連打で未来の部分を順番に消化しません。前の部分と成功可能時間が重なる場合も、手前を先に処理します。

### 3.2 判定、ライフ、得点

方向が正しいとき、到達との差の絶対値が60ミリ秒以下なら完全成功、140ミリ秒以下なら成功、それ以外は失敗とします。±60、±140は成功側に含めます。画面の言葉は「ぴったり」「成功」「早すぎました」「遅すぎました」「反対の方向です」「押す時間を過ぎました」など、原因を短い日本語で返します。方向が違う場合は方向の説明を優先します。

ライフは3です。1攻撃の中で何回失敗しても減少は最大1ですが、各回の失敗で連続成功と完全成功の連続数は切れます。ライフ0が確定した時点で終了し、残りの部分や古い入力から加点・回復しません。完全成功10回連続ごとに1回復し、上限3です。

基礎点は完全成功300・成功100、連続成功5回ごとに倍率+0.5、上限4倍、中心に近いほど最大50点を追加する既存式を維持します。各成功を連続数へ加えてから得点を計算します。例：5連続目の完全成功で誤差0なら500点です。成功数は分割部分ごとの成功を数え、攻撃本数とは別に記録します。

完全成功の割合は従来どおり「完全成功数÷成功総数」、成功ゼロは0%です。画面では「成功のうち、ぴったりの割合」と意味を示します。試行総数は成功・失敗を含む各部分の確定回数です。練習はすべての本番集計から除外します。

ランクの初期値はA版のS=18,000、A=10,000、B=5,000、C=0を引き継ぎます。速度や登場時期の調整後、必要ならR4で変更理由を記録します。得点や判定に関わる変更では端末内記録のルール版も更新します。

### 3.3 初回練習と再挑戦

ホームで名前を入力して開始します。初回は左・右の対応を学び、その後に上・左上・右上を学ぶ、計5方向の案内付き練習を行います。各方向を1回成功すると次へ進み、失敗した方向を再提示します。ライフは減らず、成功ゼロで完了しません。操作ボタンは最初から5つ固定し、練習対象だけを案内します。

練習を完了したら端末内へ完了を保存し、本番の集計をすべて0、ライフ3にして3・2・1から開始します。準備の最大コンボや回復用の連続数を持ち越しません。練習後に再び5回の準備を挟みません。

2回目以降と「もう一回」は、同じ名前でカウントダウンから直接開始します。名前の再確認や練習の強制を繰り返しません。「遊び方」から練習をやり直せます。この任意練習は完了画面に戻し、勝手に本番を開始しません。練習中はいつでもホームへ戻れます。保存が使えなくても同じ起動中は完了状態を保持します。

### 3.4 難しさと攻撃の変化

20段階を残し、序盤は遅い単発、中盤は速度の揺らぎと2連、後半は3連を組み合わせます。5方向のボタン配置は変えません。2・3連へ移る際は必要回数を予告し、説明が攻撃や押す位置を隠さないようにします。難易度20でも終了せず、ライフが残る限り続きます。時間制限モードは増やしません。

調整開始用の成功数境界は `[0,3,6,9,12,16,20,24,28,32,36,41,46,51,56,62,68,74,81,88]` とします。2連は難易度7（成功20）、3連は難易度13（成功46）から抽選候補にします。これは旧版の100回・188回をそのまま残さないための初期案であり、実測済みの最適値ではありません。

速度の開始値980ミリ秒、終盤の基準440ミリ秒を出発点とし、速度の揺らぎは序盤0から徐々に増やします。分割の間隔は初期値155〜260ミリ秒とし、必要回数が増えた瞬間に速度まで急変しないようにします。R4で20段階分の数値・確率・上下限を1つの表に固定し、確率の合計、単調性、最短の操作可能時間を検査します。

1,000通り以上の固定乱数と一定精度の自動入力で分布を調べます。完全成功を続ける基準プレイで、最初の2連を本番開始30〜60秒、最初の3連を60〜120秒程度で体験できることを中央値の調整目標とします。実プレイヤーの到達保証ではありません。中央値だけでなく10/90パーセンタイル、攻撃本数、難易度到達、回復頻度も残します。

「3連まで見せるためだけに簡単すぎる」「毎回準備が長い」「段階20で伸びしろがない」をプレイ評価で確認します。人の楽しさの評価を自動入力結果だけで合格にしません。

### 3.5 画面、名前、記録、共有

ホームはゲーム名「パリパリ」、名前欄、開始、遊び方、設定、自己ベスト、ゲームのシェア、実験場へのリンクをまとめます。名前は本番開始時に必須、前後の空白と制御文字を処理し、1〜20文字の上限を表示と保存で統一します。日本語変換と絵文字を途中で壊さず、空白だけならその場で説明します。本番中の名前は開始時の値に固定します。

結果はスコア、ランク、最大連続成功、完全成功の割合、到達した難易度、自己ベストを示します。開発用の内部値は見せません。「もう一回」「ホームに戻る」を優先して押せる位置へ置き、共有文や追加説明で下へ追い出しません。ランキング欄や「通信に失敗しました」というランキング用表示は置きません。

保存できない場合も遊べるようにし、名前の読み書きだけ例外処理を抜けないようにします。完成版の自己ベストはルール識別子付きの別領域に保存し、旧2/4方向版・旧5方向版の得点を混ぜません。旧データは削除せず、設定・名前だけ妥当性を確認して移します。新旧タブの完了順で自己ベストが下がらないよう、保存直前にも最大値を比較します。

共有先のURLは完成版の正式な公開URLを1つだけ使います。開発URL、`file://`、検査用引数、同じURLの二重挿入は避けます。公開先がR6で確認できるまでは推測URLを正式値にしません。端末の共有が使えなければコピー、コピーもできなければ現在見えている欄で手動選択へ進みます。キャンセルはエラーにしません。ホームから非表示の結果欄へフォーカスを移す代替処理は引き継ぎません。

SNS向けのタイトル・説明・プレビュー画像を整えます。画像は完成した実ゲームの5方向画面を使い、存在しないゲーム内容を描かず、新しい有料素材は使いません。プレビュー画像の制作は後続実装の範囲で、今回の計画PRでは生成しません。

## 4. 技術上の必須修正

### 4.1 入力時刻とゲームの時計を一致させる

ブラウザが記録した押下時刻を捨てず、本番開始からの経過時間へ変換します。開始・中断・再開の基準を共通化し、生のイベント時刻と停止時間を除いたゲーム時刻を直接引き算しません。描画回数を基準に時間を進めず、50ミリ秒を超えるフレーム時間を切り捨ててゲームが遅くなる処理を撤去します。粒子など見た目だけの更新量制限は許容します。

同じ時刻なら入力を期限切れより先に扱います。イベント配送の遅れで、時間内の入力を先に失敗へ確定しない方針を設計します。初期案は失敗確定に最大100ミリ秒の配送待ちを設ける方法です。入力自体の成功期限は140ミリ秒のままで、遅い押下を成功にしません。0・16・50ミリ秒の配送遅れを検査し、確定済みの結果を復活させない上限と順序をR2で明記します。同じ結果を保証できる別方式なら変更可能です。

一時的な停止を低フレームレートと混同しません。目に見える更新が長時間止まった場合は復帰時に連続被弾させず、明示的な停止へ移す規則をR2で実装します。初期案は250ミリ秒超の途絶で最後に表示した状態へ停止し、その途絶中の入力を持ち越さない方式です。判定済みの成功を無断で取り消さず、方式と境界を検査へ固定します。

収束リング、攻撃の到達、必要回数の予告は同じ時計で描きます。PERFECT演出で攻撃だけ遅らせて判定との見た目をずらすことも禁止します。次攻撃は予定された最後の到達時刻と成功期限を基準に間隔を計算し、早押しや演出の長さで出現を早めません。

参考： [DOMのイベント時刻](https://dom.spec.whatwg.org/#dom-event-timestamp)、[イベント時刻の基準](https://developer.mozilla.org/en-US/docs/Web/API/Event/timeStamp)、[描画更新の説明](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。これらは実装方法の資料であり、実機の入力遅延を測定した証拠ではありません。

### 4.2 入力と状態遷移

入力先が入力欄、選択欄、編集可能要素、日本語変換中ならゲーム用キーで既定動作を止めません。ゲーム入力の有効状態を先に確認します。押下と互換クリックの二重発火を除外しつつ、メニューボタンは通常のクリックや読み上げ操作でも使えるようにします。指を離す、画面外へ動かす、入力が取り消される、別タブへ移る各経路で押下状態を解除します。

参考： [W3C Pointer Events](https://www.w3.org/TR/pointerevents/)。イベントの互換動作を前提に、押した回数とゲーム入力件数を分離せず検査します。

状態は少なくともホーム、説明、設定、練習、開始カウントダウン、本番、一時停止、再開カウントダウン、結果を区別します。練習と本番の停止には復帰先も保持します。古いタイマー・古い入力・前の試合の結果処理が新しい試合へ作用しないよう、試合識別子と遷移の有効性を確認します。

開始前・練習・本番・再開前のいずれで離脱しても停止し、非表示のまま本番を始めません。ホームや結果は離脱だけでプレイ状態へ変わりません。画面へ戻っても自動再開せず、「再開」から準備のカウントダウンを挟みます。表示中、適切な向き、入力可能であることを再確認して1回だけ再開します。

停止中は攻撃、判定期限、出現待ち、得点、連続数、回復、難易度、ゲーム用乱数を変えません。画面の背景だけ動かす場合もゲーム用乱数を消費しません。横向きから縦向きへの復帰、同じ向きの再通知、ブラウザ復元を含めます。

参考： [HTMLのページ表示状態](https://html.spec.whatwg.org/multipage/interaction.html#page-visibility)。ブラウザの背景タイマー抑制だけに停止を任せません。

### 4.3 表示と演出をゲームの難しさから分ける

スマホは縦画面、PCは中央の縦長領域を使い、横長のPCへ回転案内を出しません。端末種別を横幅だけで決めず、タッチ・マウス・キーボードの併用も検査します。PCの余白を増やすために5方向の位置関係や判定時間を変えません。スマホの横向き時は停止して案内し、縦へ戻った後に再開します。

上部情報、攻撃領域、基準位置、操作領域を分けます。ノッチやホームインジケーターを避け、短い縦画面でも攻撃や判定文字がボタンを覆わないようにします。操作領域は原則44ピクセル以上、方向ボタンはより広くし、見た目と受付範囲を一致させます。

ゲーム中は不要なスクロール・長押し選択・ズームを防ぎます。説明・結果・名前の画面では必要な縦スクロール、文字の編集・コピーを許可します。全画面の `touch-action: none` でメニューまで止める方法は残しません。ソフトウェアキーボード表示中や文字拡大でも、入力欄と開始・戻るに届くようにします。

「画面の動きを抑える」を有効にすると揺れ・強い全画面発光・過大な拡大や粒子を抑えます。ゲーム内時間や攻撃速度・得点は変えません。成功の瞬間の静止やスローは、装飾部分に限るか廃止します。BGM・効果音は追加せず、振動非対応でも視覚だけで必要な情報が分かるようにします。

### 4.4 配布、検査、公開の境界

分割ソースを正本とし、`dist/paripari.html` はそこから再生成します。移植する共有処理を含めて依存漏れを検出し、未登録モジュールは生成時にも検査できるようにします。特定の生成器やファイル名の変更は強制せず、再生成可能性と起動確認を必須にします。

分割版と単一HTML版の両方で、ホーム→開始→成功/失敗→結果→もう一回を検査します。単一HTMLはローカルファイルとしても起動を確認し、共有や保存が使えない場合の継続を検査します。ただし、コンピューターのブラウザで開けたことをiPhoneでのファイル起動確認と報告しません。製品の主な提供方法はHTTPSの公開ページです。

変更ごとの自動検査をGitHub Actionsへ追加します。既存テスト、生成、依存の検査、ブラウザでの起動と回帰検査を含めます。PRで公開処理を実行せず、外部スコア送信が0件であることも検査します。検査用入力・固定乱数で通常の自己ベストを更新しません。検査用ハンドルを本番へ無条件公開しません。

R6では公開予定のパス、生成物、既定ブランチと公開元の違い、ライセンス表記、相対パス、プレビュー画像を確認します。現在の公開設定を推測で変更しません。完成版を公開する変更案はDraft PRと手順まで用意し、実際の反映・実験場の一覧への追加はユーザーの公開指示後に行います。ランキング登録は公開時にも本計画の対象外です。

## 5. 工程とPRの単位

各工程は実装→検査→実装と分けたレビュー→必要修正→再検査→Draft PRまで進めます。実装者の自己確認だけを独立レビューと呼びません。レビュー担当や別コンテキストを用意できなければ、その事実を未実施として残します。mainへ直接書き込まず、マージ・自動マージ・保護設定の緩和は行いません。

| 工程 | 作業と主な対象 | 完了条件 |
| --- | --- | --- |
| R1 基準を統合する | A本体へBの名前・共有・実験場リンクを必要部分だけ移植。ランキング部分は移植しない。生成処理と初期の自動検査を整える | 5方向・分割攻撃を保持し、分割版/単一HTMLが起動する。移植元一覧と差分を記録。名前入力・PC表示の暫定障害も解消する |
| R2 入力と時間を直す | 共通時計、時刻変換、境界、連続入力、停止/再開、演出と進行の分離 | 同一入力記録の判定が30/60/120回毎秒で一致。離脱・回転・多重操作で進行や得点が変質しない |
| R3 一巡して遊べるようにする | ホームの名前、練習、結果、再挑戦、保存、共有、短画面の縦移動、PC用の表示 | 名前入力から結果・再挑戦まで通る。練習の記録が本番に混ざらず、通信や保存の失敗でも遊べる |
| R4 難しさと説明を調整する | 20段階の表、2/3連の登場時期、必要回数・失敗理由の予告、無音の視覚演出 | 数値・確率の検査と1,000系列の記録を提出。説明が実装に一致し、動きの設定で判定差がない |
| R5 公開候補を検証する | 全回帰、自動操作、画面サイズ、長時間・再挑戦負荷、独立レビュー | 必須自動検査が全て通る。重大な未解決事項を0にする。実機未検査は別項目で残す |
| R6 公開できる状態に整える | iPhone実機確認記録、配布物一致、ライセンス、公開手順、実験場へのリンク、プレビュー | 完成条件を満たすコミットと検査結果を固定。実機未確認なら公開保留。実際の公開は別の明示指示後 |

R1で作る画面の最低限の整合と、R3で完成させる画面品質を区別します。途中PRのマージを完成宣言にしません。先行工程のマージを確認してから次の工程の比較先を更新し、同じ修正を別PRに重複させません。

## 7. 完成条件と報告

完成とするには、5方向・単発/2連/3連・20段階を備え、名前入力から練習、本番、結果、再挑戦まで通して遊べることが必要です。判定・ゲーム内時間・見た目が一致し、設定や描画頻度で同じ入力の結果が変わらず、離脱・回転・連打で不正な進行が起きないことを確認します。

分割ソースと単一HTML、スマホ表示とPC表示の検査を通し、重要なボタンや説明に届かない状態を残しません。保存・共有が非対応でも遊べること、外部スコア送信がないこと、無音方針と旧データ保全を確認します。

コードの完成、自動検査合格、独立レビュー完了、実機確認、公開反映を別々に記録します。iPhone 17 Pro Safari実機の確認を画面サイズの模擬だけで代替しません。実機が使えない場合も実装とDraft PRまでは進め、実機項目を未実施として公開を保留します。

後続報告には対象コミット、変更点、実行コマンドと結果、検査環境、レビュー結果、未実施事項、次の工程、Draft PRを記載します。必要な修正を終えるまで再検査し、「生成成功」だけを「ゲーム完成」と言い換えません。
