# PR #7 マージ後のブラウザ検査修正

実施日：2026-09-27（日本時間）  
基準：main `f648eb62a8c1219f41f7075a420d66fba28d90e6`

## 確認した失敗

[マージ後のQuality](https://github.com/chameleonjp-lab/paripari/actions/runs/35644103544)の初回実行では、単体検査・生成一致・Chromiumは成功し、macOS WebKitは14件成功・1件失敗でした。分割版の成功入力検査が、`successCount`の増加を8秒待って失敗しています。前のPRでWebKitをmacOSへ移しただけでは、検査の不安定さは解消していませんでした。

旧検査は、現在から80ミリ秒後に到達する攻撃を準備し、ブラウザ外から状態を読み、到達20ミリ秒前を待ち、別の通信でキーを送っていました。その通信・描画待ち時間にゲーム時計が進むため、検査自身が入力期限を逃す競合があります。失敗時の入力発生時刻は旧ログにないため、その1回の入力遅れを数値で断定することはできません。

通常起動の診断には258ミリ秒の描画途絶と安全停止も記録されています。これは製品の「250ミリ秒を超える途絶は停止する」規則と整合します。検査環境の描画停止と、操作・判定の機能検査を区別する必要があります。

同じmainを2026-09-27に再実行した第2回も、WebKitは14件成功・同じ分割版1件失敗でした。この回はゲーム開始後の538ミリ秒の描画途絶、`Session=PAUSED`、`pauseReason=stall`、ゲーム時刻83ミリ秒・ライフ3での停止を記録しています。攻撃判定を待つ前に安全停止したことを確認でき、macOSへの移行だけでは解消しないことも再現しました。

## 修正の範囲

- 時刻に依存する成功・誤方向・期限切れ・3連・結果・再挑戦・練習完了の検査だけ、ブラウザの時間を制御します。ページを読む前に制御時計を導入し、HOMEで止めてから、通常進行では全描画処理を順番に実行します。
- 製品の`GameClock`、入力イベントの配線、判定処理、画面処理は置き換えません。ただし制御時計はブラウザの`performance`・`requestAnimationFrame`・`Event.timeStamp`などを置き換えるため、この検査を実機の入力遅延測定とは扱いません。
- 実時間での通常起動、キー・タッチ入力の受け渡し、ページ離脱・縦横変更、共有、`file://`での起動を残します。
- 別の回帰検査で1秒の描画途絶を作り、最後の描画時点で止まること、未確定入力を捨てること、得点・ライフ・攻撃判定を進めないこと、自動再開しないこと、明示再開からカウントダウンを経ることを確認します。
- 攻撃を準備する検査コードは、GameとSessionが実際に実行中であることを要求します。停止中のGameを検査側から`PLAYING`へ書き換える処理を取り除きます。

判定幅±140ミリ秒、配送保証50ミリ秒、描画途絶250ミリ秒の境界は変更しません。検査の削除、失敗を成功へ変える扱い、自動再試行による失敗の無視も行いません。製品ソース・配布HTML・ランキング・公開設定は変更対象外です。

制御時計の仕様は[Playwright公式資料](https://playwright.dev/docs/clock)と[Clock API](https://playwright.dev/docs/api/class-clock)を参照しました。通常進行の`runFor`と、途絶を作る`fastForward`を区別しています。

## 検証の記録

基準版のローカル単体69件と`build:check`は成功しています。修正後の検査・独立レビュー・提出コミットのQuality結果は、この修正PR本文に記録します。実装はLuna Max、独立レビューはSol Highへ分けます。

元のmainに対する再実行は、同じコードで成否が変わるかを確認するための比較です。その結果だけで再発防止が完了したとは扱いません。修正版をmainへ反映するには、この修正PRのマージが必要です。作業側からマージ・mainへの直接変更は行いません。

iPhone 17 Pro Safari実機での性能・物理入力遅延、Linux WPEの描画性能は、この修正によって確認済みにはなりません。
